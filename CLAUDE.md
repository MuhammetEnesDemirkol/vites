# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Vites, a Claude Code mod that picks the model and reasoning effort for each prompt the person types, with a footer chip to toggle it. Slash command: `/vites aç|kapat|durum|tavan|günlük|rapor`. All user-facing text is Turkish.

It is derived from Model Gear 0.2.3 (MIT, Muhammad Moussa, `muhamoussa7/claude-model-gear`). The design document is `docs/superpowers/specs/2026-11-01-vites-design.md`; it wins over this file on behaviour. The marketplace is `.claude-plugin/marketplace.json` (named `demirkol`), and the plugin lives in `vites/`.

## Commands

There is no build step, no bundler and no installed dependencies. TypeScript is checked and tests are run by the `claude` CLI itself:

```
claude plugin validate vites
claude plugin test vites
```

Tests import from `claude-code/testing`, which only exists under `claude plugin test`, so `node`, `tsc` and `bun test` will not work. `claude plugin test` has no filter option; it runs every `*.test.ts` under the folder.

## Releases

Bump `version` in `vites/.claude-plugin/plugin.json` for every release. Installed copies are cached by version, so an unchanged version can keep the old code in place.

The `vites/.claude-plugin/types/` folder is generated by Claude Code and listed in the root `.gitignore`. It is there so the editor can type-check the `claude-code` imports; the tests do not depend on it. Keep it in the working copy, do not commit it.

## Plugin layout

- `vites/.claude-plugin/plugin.json` declares name, version and `"types": "./types/index.d.ts"`.
- `vites/.claude-plugin/types/` is generated typings for the `claude-code` host API. Treat it as read-only reference and search it when you need an engine API.
- `vites/hooks/hooks.json` lists `./register.tsx` as the one module.
- `vites/hooks/register.tsx` exports `register: Register` and wires event hooks with `on(...)`. It is the only file that talks to the engine: it reads and writes `$.store` and `$.state`, calls `$.config`, `$.model.complete`, `$.ui`, and delegates every decision to the pure modules below.
- `vites/hooks/logic.ts`: classifier prompt and answer parsing, keyword fallback in English and Turkish (`guessLevel`, `guessEffort`, `namedEffort`), `isShortReply`, model matching (`lineOf`, `candidatesFor`, `restoreValue`), `gearNumber`, `effortTr`, `chipLabel`, `statusLine`, `fold`.
- `vites/hooks/gear.ts`: `parseTags` (the `#etiket` syntax), `parseCeiling`, `capLevel`, `nextGear` (ceiling plus delayed downshift over a `GearState`), `readGearState`, and the constants `DROP_AFTER`, `DEFAULT_CEILING`, `HOLD_EFFORT`.
- `vites/hooks/journal.ts`: `JournalEntry`, `makeSnippet` (120 chars), `appendEntry` (500 limit), `readJournal`, `formatJournal`, `parseCount`.
- `vites/hooks/usage.ts`: the token book (`UsageBook`, day x source x line), `tokensFrom`, `addUsage`, `readUsage`, `baselineLine`, `localDay`.
- `vites/hooks/pricing.ts`: `PRICES` per line, `PRICE_DATE`, `cost`. Prices are copied from the `claude-api` skill, never from memory; the comment names the source.
- `vites/hooks/report.ts`: `parsePeriod`, `daysOf`, `computeReport`, `formatReport`.
- Tests: `vites.test.ts` (logic plus end-to-end through the mock engine), `gear.test.ts` (tags, ceiling, downshift), `records.test.ts` (journal, usage, pricing, report).
- `vites/types/index.d.ts` defines the plugin's own types (`Level`, `Effort`, `Line`, `GearNumber`, `PickSource`, `PickFlag`, `LastPick`) and augments `PluginState` in the `claude-code` module. The `atom({ plugin: 'vites', key })` calls in `register.tsx` must use literals that match that interface.

JSX uses a custom factory (`jsxFactory: "h"`). Components are not imported: `$.ui.resolve(e)` returns `Box`, `Text`, `Button` and `Input` for the current surface.

## Conventions

- Every hook handler wraps its work in `try`/`catch` and falls through to `next(e)`, and each `on(...)` ends in `.catch(...)` that does the same. A failure in the mod must never block the person's prompt.
- Validator rule: `$` is never passed into a closure. It goes only to functions declared at the top of the file (or imported from the plugin's own files), never to a lookup table of handlers or a callback that captures it, so the command router is a `switch`. The chip's `onPress` only calls the top-level `toggle($)`.
- State lives in two places. `atom` plus `read`/`update` (`$.state`) drives the UI (`enabled` for the chip, `last` for the status line and `turn.step`). `$.store` persists across sessions and reloads. Writers update both; `session.start` rehydrates only `enabled` from the store, and `last` starts empty each session.
- User-facing strings are short Turkish sentences that say what happened and what was left unchanged. Command arguments are read through `fold()`, so `ac`, `aç` and `on` are the same word.
- Levels are shown to the person as gears: 1 = haiku, 2 = sonnet, 3 = opus, 4 = fable (`gearNumber`). Efforts are shown with `effortTr` (düşük, orta, yüksek, çok yüksek, maks).
- Flags are named `isX`, matching the typings (`isLocked`, `isEnabled`).

## How it works

The flow on `prompt.submit` (`register.tsx`, hook then `pickModel`):

1. The hook skips unless Vites is on and the prompt was typed while idle (`isTypedWhileIdle`: composer or bridge origin, no `turnId`, not a slash command). `parseTags` (`gear.ts`) reads leading `#etiket`s. A short acknowledgement (`isShortReply`, English and Turkish words) is skipped unless it carries a tag. When a tag was found and text remains, the text after the tags is what goes on to the model; a tag-only prompt goes through as typed.
2. `rawPick`: with a model tag, the level is the tag's line and the small model is not called (`source: 'tag'`). Otherwise `askSmallModel` asks the smallest model in the install's `model` config row for "level effort" in two words (4s timeout, its usage counted as `classifier`); if that gives nothing, `guessLevel` and `guessEffort` in `logic.ts` fall back to keyword regexes on `fold()`ed text (`source: 'keywords'`, else `'classifier'`).
3. `nextGear` (`gear.ts`) turns the raw pick into the gear to run: a model tag sets and holds the gear outright, above the ceiling if need be; otherwise the pick is capped at the ceiling (`ceilingOf`, default `opus`), then compared with the held gear in the stored `GearState`: equal or higher is taken at once, lower is held, and the `DROP_AFTER`-th (3rd) light pick in a row drops to the highest of them. An effort tag or an effort named in the prompt (`namedEffort`: "ultrathink", "max effort", "yüksek efor") is `fixedEffort`: sent as is, never held. Effort is otherwise held with the model (`HOLD_EFFORT`, see the comment in `gear.ts` for why).
4. `candidatesFor` orders model options for the level and `config.set` tries each until one is accepted; a model already in use is not set again.
5. The pick is kept in the `last` atom as a `LastPick` with `gear`, `source` (`classifier`, `keywords` or `tag`) and `flags` (`capped`, `held`, `dropped`, `tagged`); `applied` and `effort` go to the store; `showLine` pins the status line. `keepRecords` then writes the new `GearState` under `gear` and appends a `JournalEntry` (`makeSnippet`: first 120 characters) under `journal`, each in its own try so a failed write cannot undo the switch.

Usage recording on `turn.step`: after `next(e)` yields the result, `recordStep` adds `result.usage` to the day's `UsageBook` under `main` when `e.agentId` is undefined and `subagent` otherwise (the marker, not the model, decides), keyed by the answering line. Only while Vites is on and the model is on a known line. The day's `baseline` is `baselineLine(previous)` and is set once per day.

Details that need several files to see:

- Models are matched by line name (`haiku`, `sonnet`, `opus`, `fable`) found inside the option string, so new versions work without code changes. Level to line is the `LEVEL_LINE` table.
- The engine has no effort row in `/config`. Effort is injected per request in the `turn.step` hook (`effortToSend`) for the main loop and its subagents alike. It is never saved in settings. Subagents keep their own model. The effort sent is also written to the store under `effort` for the person's status bar, and deleted when Vites turns off. The gear, model and effort of the last prompt are pinned under the prompt with `$.ui.status` (`statusLine`, e.g. `3. vites · opus · yüksek`), cleared when off.
- `applied` in the store is the model Vites last set. A hand `/model` or `config.set` from the composer turns the plugin off without restoring, and a toast says why; the plugin's own `config.set` has another origin and does not. A model that differs on the next prompt without such a call (seen after `/compact`, or from another window sharing the setting) does not turn it off; it sorts the prompt again. A bare `/effort` counts only if the saved effort actually changed, since the menu can be cancelled.
- Turning on saves the current model as `previous` and resets `gear`. Turning off through the command or the chip restores it via `restoreValue` and deletes `previous`, `applied`, `effort`, `gear`; `ceiling`, `journal` and `usage` survive.
- `parseTags` keys its lookups in `Map`s and keeps digits, so `#constructor` and `#sonnet14` are plain text.

Store keys: `enabled`, `previous`, `applied`, `effort`, `ceiling` (line name or `'yok'`), `gear` (`GearState`), `journal` (`JournalEntry[]`, newest last), `usage` (`UsageBook`).
